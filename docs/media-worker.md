# Media worker behavior

The worker accepts authenticated 8 kHz mono linear16 audio only for an API-confirmed running call. One call has one audio socket at `/audio/<callId>`, started when the call is answered and closed with the channel. It holds at most five concurrent calls, matching the trunk ceiling, and 25 total reservations including receipts awaiting an API reply. A call releases its capacity as soon as its audio ends, even while a transcript receipt is still in flight.

Every accepted call has a three-second provider connection deadline and an audio lifetime of `MKTR_MAX_CALL_SECONDS` (default 180 s); PCM is capped at that duration plus a tenth, so the gateway's own scheduled duration limit ends the call first. Two seconds of audio may be buffered while the provider opens, and each WebSocket message is capped at 64 KB. Zero-length frames are ignored. Deepgram outbound buffering is capped at 256 KB, and finalized transcript text is capped at 2,000 characters. These bounds stop a stalled or malformed source from accumulating unbounded audio or text.

Caller disconnect and worker shutdown cancel pending provider connections. A provider that resolves after cancellation is immediately closed without receiving buffered audio, and a replaced connection's callbacks are ignored. Synchronous provider write/close failures are contained and logged with the call ID and, when one is open, the listen window. Audio, listen windows and receipt delivery have separate lifetimes: neither closing a window nor ending the audio cancels a receipt already in flight.

Transcript delivery uses one generated `utteranceId` across at most three attempts, with 100 ms and 200 ms retry delays. Network failures and HTTP 5xx responses are retried; other HTTP 4xx responses terminate delivery. HTTP 409 means the listen window has closed and needs no further delivery. Each API attempt has a three-second deadline covering both response headers and body handling. Provider or delivery failures send the existing generic media-error notification for the window that was open; failed notifications are logged, and the API's listen timeout remains the fallback. Shutdown cancels pending HTTP work.

## One speech stream, many listen windows

A listen window is a logical gate, not a connection. The orchestrator opens one on the worker with `POST /calls/<callId>/window/<windowId>?endpointingMs=<n>` when it enters a listen node and closes it with `DELETE` on the same path when it leaves; both use the media gateway bearer token over the private network. The worker submits at most one transcript per window, naming that window in the receipt, and the API's own `listenWindowId` and status guard refuse anything that arrives for a window it is no longer waiting on.

Speech the provider finalizes while no window is open is discarded without an API request. That is speech from clip playback or the tail of the previous turn, and it answers a prompt that has already been routed.

Audio is forwarded to the provider continuously, including during clip playback, because [Deepgram warns that gating audio through a voice activity detector harms accuracy](https://developers.deepgram.com/docs/understand-endpointing-interim-results): the silence between words is context the model uses. Only the read (callee) leg is streamed, so MKTR's own clips are never sent. The cost of this is provider minutes: a call bills for its whole answered duration rather than for its listen windows alone.

An answered call whose flow has no listen node opens no audio stream at all, and a call whose provider connection is not open drops inbound PCM rather than buffering it.

## Listen window settings

Before it accepts audio, the worker asks `GET /api/media/calls/:id/window` for the call's state and refuses the socket for a call that is not running. The reply carries the endpointing the connection should use now: the open window's value when the call is already listening, otherwise the first listen node's value, so the connection opens during the greeting and the first reply costs no handshake. A listening reply that omits the value or puts it outside 100–1000 ms refuses the socket with 409 and is reported with the call and window IDs.

Each reply records which marker ended it. `finalizedBy` is `endpoint` when the configured endpointing silence closed the utterance and `utterance_end` when Deepgram's fixed 1000 ms UtteranceEnd fallback did, meaning endpointing was not the binding limit for that turn. It travels on the transcript receipt to the API's `Turn completed` log line, sits beside each utterance in the capture sidecar, and is printed by the replay tool, so one call shows whether lowering endpointing can help at all.

Endpointing is the silence after the caller stops before the reply is final. A short window returns yes/no answers quickly but truncates longer replies, because the first finalized utterance completes the window and later speech waits for the next one. The range stops at 1000 ms because Deepgram's UtteranceEnd fallback, fixed at 1000 ms, would otherwise finalize ahead of the endpoint.

Deepgram fixes endpointing when the connection is established, so a listen node whose value differs from the open connection's makes the worker reconnect for that node; the flow editor's listen inspector says so. A flow whose listen nodes share one value, which is every flow that leaves the field alone, uses a single connection from answer to hangup.

The Deepgram origin comes from `MKTR_DEEPGRAM_BASE_URL` (default `https://api.au.deepgram.com`, Sydney). The geographic premise for that default was measured false from the droplet on 12 Sep 2026, and the endpoint is open pending a steady-state replay on an already-established connection; data residency is a separate PDPA question. The Latency 1 entries in `docs/decisions.md` carry the measurements and what still has to be decided. The worker appends `/v1/listen`, fails startup in every mode on a value that is not a bare https or wss origin, and allows cleartext `http`/`ws` only for loopback fakes so the API key never leaves the host unencrypted.

## Latency meaning

`sttLatencyMs` estimates the delay from the final recognized word's audio time to the completed utterance. It includes endpointing, network transport, and audio buffered while the provider connects. The worker preserves the original PCM arrival timestamp; Deepgram maps its last finalized word's `end` (or `UtteranceEnd.last_word_end`) onto the audio timeline anchored at the first PCM frame, subtracting that frame's duration. Later silence frames do not reset this anchor.

This is an estimate for contiguous real-time PCM, not a measurement of provider compute time. Word alignment, packet jitter, and gaps in the audio timeline affect precision. Missing word timing, a timestamp beyond submitted audio, or an estimate outside 0–60 seconds produces no latency sample. Deepgram documents [word timestamps relative to the audio stream](https://developers.deepgram.com/reference/speech-to-text/listen-streaming) and explains the [limits of client-side latency measurements](https://developers.deepgram.com/docs/measuring-streaming-latency). Production speech timing and accuracy remain operator checks.

## PCM capture and offline replay

`MKTR_PCM_CAPTURE_ENABLED=true` tees every accepted inbound frame to `MKTR_PCM_CAPTURE_DIR` (default `storage/pcm-capture`, ignored by Git; Compose mounts the `pcm-capture-data` volume) as `<callId>/<streamId>.pcm`, raw linear16 8 kHz mono exactly as the provider receives it, including frames buffered while the provider opens. One file covers the whole call. A `<streamId>.json` sidecar lists each frame's byte offset, size and arrival time in milliseconds after the stream opened, plus every utterance the provider finalized with its worker latency estimate and the listen window it belonged to; an utterance with no window was discarded, which is how barge-in during playback shows up. Session recordings from `uuid_record` are mixed audio and are not a substitute. Capture is a diagnostic: a write failure is logged with the call and stream IDs and stops that call's capture without affecting the call. Files are never purged automatically; delete the directory or volume when the corpus is no longer needed, as it contains callee speech.

`npx tsx scripts/replay-stt.ts <stream>.pcm` streams a capture into a speech engine at the recorded pacing and prints the time from the true end of speech to the usable transcript. The end of speech comes from frame energy, independent of any engine (override with `--speech-end-ms`); `--connect concurrent` opens the engine while audio streams as the worker does, `--connect first` isolates engine latency; `--endpointing-ms`, `--utterance-end-ms` and `--model` vary Deepgram settings from their production defaults; `--runs` repeats and summarises; `--json` prints the raw measurements. Bare `.pcm` files and 8 kHz mono 16-bit WAV files replay with contiguous real-time pacing, so a synthetic corpus works before any live capture exists. Silence is appended in real time after the capture ends until the engine finalizes, bounded by `--pad-silence-ms`. A whole-call capture holds several turns, so pass `--speech-end-ms` to time a turn other than the first. The deepgram engine needs `DEEPGRAM_API_KEY` and each run spends provider minutes.

`npm run test:media` exercises real loopback audio/provider WebSockets, fake speech streams, and fake HTTP receipt handling. The suite includes stream survival across several listen windows in one call, transcripts finalized outside a window, reconnection for a differing endpointing, lost replies, late provider opening, cancellation, failing writes and cleanup, malformed responses, buffer/deadline limits, and silence-aware timing. It uses no real speech provider credentials. End-to-end orchestration is verified against fake ESL, a fake media worker and fake STT; the first live check remains in the operator runbook.
