# Media worker behavior

The worker accepts authenticated 8 kHz mono linear16 audio only for an API-confirmed listen window. It holds at most five active audio windows and 25 total window reservations, including transcript receipts awaiting a reply. Completed utterances release their audio slot immediately, so the API can open the next listen while returning the previous receipt. The old window remains reserved against duplicate sockets until its receipt completes.

Every accepted audio window has a three-second provider connection deadline and a 65-second maximum collection lifetime; the API's shorter listen timeout normally closes it first. PCM is limited to sixty seconds per window, two seconds while the provider opens, and 64 KB per WebSocket message. Zero-length frames are ignored. Deepgram outbound buffering is capped at 256 KB, and finalized transcript text is capped at 2,000 characters. These bounds stop a stalled or malformed source from accumulating unbounded audio or text.

Caller disconnect and worker shutdown cancel pending provider connections. A provider that resolves after cancellation is immediately closed without receiving buffered audio. Synchronous provider write/close failures are contained and logged with the call and window IDs. Opening, input, and receipt delivery have separate lifetimes: closing the audio source does not cancel a completed utterance's pending receipt.

Transcript delivery uses one generated `utteranceId` across at most three attempts, with 100 ms and 200 ms retry delays. Network failures and HTTP 5xx responses are retried; other HTTP 4xx responses terminate delivery. HTTP 409 means the listen window has closed and needs no further delivery. Each API attempt has a three-second deadline covering both response headers and body handling. Provider or delivery failures send the existing generic media-error notification for that exact window; failed notifications are logged, and the API's listen timeout remains the fallback. Shutdown cancels pending HTTP work.

## Listen window settings

Before it accepts audio, the worker asks `GET /api/media/calls/:id/window` for the call's state. A listening reply carries the listen node's `endpointingMs` (the node's own value, or 300 ms when the node leaves it unset), and the worker forwards it to the provider for that window alone; a listening reply that omits the value or puts it outside 100–1000 ms refuses the socket with 409 and is reported with the call and window IDs. Endpointing is the silence after the caller stops before the reply is final. A short window returns yes/no answers quickly but truncates longer replies, because the first finalized utterance completes the window and later speech is dropped. The range stops at 1000 ms because Deepgram's UtteranceEnd fallback, fixed at 1000 ms, would otherwise finalize ahead of the endpoint.

The Deepgram origin comes from `MKTR_DEEPGRAM_BASE_URL` (default `https://api.au.deepgram.com`, Sydney, about 94 ms from Singapore against 180–240 ms to the US). The worker appends `/v1/listen`, fails startup in every mode on a value that is not a bare https or wss origin, and allows cleartext `http`/`ws` only for loopback fakes so the API key never leaves the host unencrypted.

## Latency meaning

`sttLatencyMs` estimates the delay from the final recognized word's audio time to the completed utterance. It includes endpointing, network transport, and audio buffered while the provider connects. The worker preserves the original PCM arrival timestamp; Deepgram maps its last finalized word's `end` (or `UtteranceEnd.last_word_end`) onto the audio timeline anchored at the first PCM frame, subtracting that frame's duration. Later silence frames do not reset this anchor.

This is an estimate for contiguous real-time PCM, not a measurement of provider compute time. Word alignment, packet jitter, and gaps in the audio timeline affect precision. Missing word timing, a timestamp beyond submitted audio, or an estimate outside 0–60 seconds produces no latency sample. Deepgram documents [word timestamps relative to the audio stream](https://developers.deepgram.com/reference/speech-to-text/listen-streaming) and explains the [limits of client-side latency measurements](https://developers.deepgram.com/docs/measuring-streaming-latency). Production speech timing and accuracy remain operator checks.

## PCM capture and offline replay

`MKTR_PCM_CAPTURE_ENABLED=true` tees every accepted inbound frame to `MKTR_PCM_CAPTURE_DIR` (default `storage/pcm-capture`, ignored by Git; Compose mounts the `pcm-capture-data` volume) as `<callId>/<windowId>.pcm`, raw linear16 8 kHz mono exactly as the provider receives it, including frames buffered while the provider opens. A `<windowId>.json` sidecar lists each frame's byte offset, size and arrival time in milliseconds after the window opened, plus the live transcript and worker latency estimate. Session recordings from `uuid_record` are mixed audio and are not a substitute. Capture is a diagnostic: a write failure is logged with the call and window IDs and stops that window's capture without affecting the call. Files are never purged automatically; delete the directory or volume when the corpus is no longer needed, as it contains callee speech.

`npx tsx scripts/replay-stt.ts <window>.pcm` streams a capture into a speech engine at the recorded pacing and prints the time from the true end of speech to the usable transcript. The end of speech comes from frame energy, independent of any engine (override with `--speech-end-ms`); `--connect concurrent` opens the engine while audio streams as the worker does, `--connect first` isolates engine latency; `--endpointing-ms`, `--utterance-end-ms` and `--model` vary Deepgram settings from their production defaults; `--runs` repeats and summarises; `--json` prints the raw measurements. Bare `.pcm` files and 8 kHz mono 16-bit WAV files replay with contiguous real-time pacing, so a synthetic corpus works before any live capture exists. Silence is appended in real time after the capture ends until the engine finalizes, bounded by `--pad-silence-ms`. The deepgram engine needs `DEEPGRAM_API_KEY` and each run spends provider minutes.

`npm run test:media` exercises real loopback audio/provider WebSockets, fake speech streams, and fake HTTP receipt handling. The suite includes lost replies, late provider opening, cancellation, failing writes and cleanup, malformed responses, buffer/deadline limits, and silence-aware timing. It uses no real speech provider credentials. End-to-end orchestration is verified against fake ESL and fake STT; the first live check remains in the operator runbook.
