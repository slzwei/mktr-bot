# Answering-machine detection and recordings

The FreeSWITCH adapter starts `mod_avmd` on each outbound answer, before running the flow. The overlay configures the outbound callee leg. A `CUSTOM avmd::beep` event with `Beep-Status: DETECTED` ends the call once and records `voicemail`; ordinary provider hangup events cannot overwrite an already requested voicemail/flow-failure/stop outcome. This is beep detection, so machines without a detected beep can follow the ordinary transcript or timeout path. The flow starts while detection listens. Detection accuracy, false positives and greeting timing require Shawn's controlled operator check; fake ESL verifies event handling only. The implementation follows the [FreeSWITCH mod_avmd interface](https://developer.signalwire.com/freeswitch/module-reference/applications/mod_avmd/).

Provider causes `USER_BUSY` and `BUSY_EVERYWHERE` become `busy`; `NO_ANSWER`, `NO_USER_RESPONSE`, `PROGRESS_TIMEOUT` and recovery timer expiry become `no_answer`. Unexpected failures become `failed`. Normal completions retain the final classified intent when available. `status` describes the call lifecycle; `outcome` describes its business or provider result. Campaigns retry only busy/no-answer results within their configured cap.

Session recording defaults to off. Shawn may set `MKTR_RECORDING_ENABLED` to `true` only after reviewing MKTR's recording notice and retention needs. On answer, the API persists a generated recording filename and expiry, then starts `uuid_record` on the channel; a recording command failure ends the call and records the error. Channel hangup ends the recording. No client-supplied file path is accepted. See the [FreeSWITCH audio-file API reference](https://developer.signalwire.com/freeswitch/media-and-codecs/audio-files/).

The shared `recording-data` volume is mounted at `/app/storage/recordings` in the API and `/var/lib/freeswitch/recordings/sessions` in FreeSWITCH, with UID 1000 ownership. `MKTR_RECORDING_STORAGE_DIR` changes the API path for local development; keep Compose's paired mounts aligned on deployment. Recordings use generated UUID WAV filenames. Authenticated operators download ended, unexpired recordings from call history; active calls return 409 and expired/missing recordings return 404. Responses use `Cache-Control: no-store`.

`MKTR_RECORDING_RETENTION_DAYS` defaults to 30 and accepts 1–365. A purge runs at API boot and hourly, removes expired ended-call audio, clears its metadata and removes orphan WAV files older than the retention period. Active call files are retained until termination. Reducing the configured retention also shortens existing files' deadline. Purge failures are logged and retried on the next interval; startup refuses to serve if the initial purge fails. Shutdown waits for the job before closing Postgres. The job also covers optional callback messages once inbound callbacks are configured.

The standard backup contains Postgres and the clip library, not the recording volume. A restored call may therefore retain historical recording metadata whose bytes are unavailable; the download returns 404 and the purge clears expired metadata. Keep any separately exported copies subject to MKTR's retention process; the application cannot purge files outside its volume.

Tests use fake ESL events and temporary fixture files. No actual callee audio, voicemail detector or real recording has been verified here. Follow `docs/runbook-first-live-call.md` for the operator checks.
